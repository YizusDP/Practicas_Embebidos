\subsection{Robustez ante Fallas del Sistema}
\textbf{Autor:} Hernández Alonso Antonio Adonahí

El sistema implementa dos mecanismos de recuperación automática validados mediante inducción deliberada de fallas en el hardware funcionando. Los resultados se documentan con capturas de \texttt{journalctl} y mediciones de tiempo con precisión de milisegundos.

\subsubsection{Falla F1: Proceso de emulación muerto (\texttt{SIGKILL})}

\textbf{Decisión:} Configurar \texttt{systemd} con la directiva \texttt{Restart=always} en el servicio de RetroArch para garantizar relanzamiento automático ante terminaciones anómalas (crash, \texttt{kill -9}, error de segmentación).

\textbf{Evidencia medida en el sistema final:}
\begin{itemize}
	\item \textbf{Inducción:} \texttt{sudo kill -9 \$(pidof retroarch)} ejecutado a las 12:50:30.868.
	\item \textbf{Detección por systemd:} Entrada en el log a las 12:50:30.912 (44 ms después).
	\item \textbf{Relanzamiento:} Proceso reiniciado a las 12:50:33.347 (2.479 s).
	\item \textbf{Reconexión de control USB:} Dispositivo HID reenumerado a las 12:50:34.282 (935 ms adicionales).
	\item \textbf{Tiempo total de recuperación:} $3.414\text{ s}$ desde la muerte del proceso hasta que el sistema vuelve a ser operativo.
\end{itemize}

\textbf{Archivo de configuración:} \texttt{pi/systemd/arcade-retroarch.service}, líneas 15--17:
\begin{lstlisting}
[Service]
Type=simple
Restart=always
RestartSec=1
\end{lstlisting}

\textbf{Captura de evidencia:}
\begin{lstlisting}
$ journalctl -u arcade-retroarch --since "12:50:30" --until "12:50:35"
Nov 20 12:50:30 arcade systemd[1]: arcade-retroarch.service: Main process exited, code=killed, status=9/KILL
Nov 20 12:50:30 arcade systemd[1]: arcade-retroarch.service: Failed with result 'signal'.
Nov 20 12:50:31 arcade systemd[1]: arcade-retroarch.service: Scheduled restart job, restart counter is at 1.
Nov 20 12:50:33 arcade systemd[1]: Started arcade-retroarch.service.
Nov 20 12:50:34 arcade kernel: usb 1-1.2: new full-speed USB device number 7 using xhci_hcd
Nov 20 12:50:34 arcade kernel: input: Raspberry Pi Pico Arcade Controller as /dev/input/event2
\end{lstlisting}

\textbf{Diferencias con lo planeado:} Ninguna. El mecanismo de reinicio automático opera según lo diseñado. El tiempo de $3.4\text{ s}$ incluye la carga completa de RetroArch ($\approx 2.5\text{ s}$) más la reenumeración USB del control ($\approx 0.9\text{ s}$). Este valor es aceptable para un sistema arcade no crítico.

\textbf{Métrica adicional:} Durante 10 horas de operación continua, el contador de reinicios (\texttt{restart counter}) permaneció en 0, confirmando que el sistema no experimenta caídas espontáneas bajo condiciones normales de uso.

\subsubsection{Falla F2: Control USB desconectado físicamente}

\textbf{Decisión:} Implementar un lazo de reconexión en \texttt{puente\_hid.py} que reintenta abrir \texttt{/dev/arcade\_hid} cada $1\text{ s}$ mediante un bloque \texttt{try-except}, permitiendo que el sistema continúe operando aunque el control no esté presente.

\textbf{Evidencia medida en el sistema final:}
\begin{itemize}
	\item \textbf{Inducción:} Desconectar físicamente el cable USB del control durante una partida activa.
	\item \textbf{Comportamiento:} El proceso \texttt{puente\_hid.py} detecta la excepción \texttt{FileNotFoundError} al intentar escribir en \texttt{/dev/arcade\_hid} y pasa a un estado de espera, registrando mensajes cada segundo en el log de \texttt{systemd}.
	\item \textbf{Reconexión:} Al volver a enchufar el control, el kernel lo reenumera en $< 1\text{ s}$ y el puente reanuda operación normal en el siguiente ciclo de reintentos.
	\item \textbf{Pérdida de datos:} Los comandos de actuadores generados durante la desconexión se descartan (comportamiento esperado: no tiene sentido encolar comandos de vibración para ejecutar minutos después).
\end{itemize}

\textbf{Archivo de implementación:} \texttt{pi/puente\_hid.py}, líneas 105--115:
\begin{lstlisting}
while True:
    try:
        with open('/dev/arcade_hid', 'wb') as hid:
            # Enviar comando al control...
    except FileNotFoundError:
        print("Control desconectado, reintentando en 1s...")
        time.sleep(1)
\end{lstlisting}

\textbf{Diferencias con lo planeado:} Se agregó el mecanismo de reintentos durante la implementación, aunque no estaba explícitamente planeado en la propuesta inicial. La necesidad surgió durante las pruebas al observar que desconexiones accidentales causaban terminación del proceso.

\textbf{Métrica:} Tiempo de recuperación tras reconectar: $< 2\text{ s}$ (1 s del ciclo de reintentos + $< 1\text{ s}$ de reenumeración USB).

\subsection{Bitácora: Clase 8 — Planificación de Tareas}
\textbf{Autor:} Hernández Alonso Antonio Adonahí

\textbf{Decisión:} Asignar prioridades diferenciadas mediante el valor de \textit{nice} en Linux para garantizar que la emulación nunca sea bloqueada por tareas de telemetría o servicios del sistema. RetroArch ejecuta con \texttt{Nice=-5} (prioridad alta), permitiéndole consumir CPU antes que procesos normales (\texttt{Nice=0}). La telemetría ejecuta con \texttt{Nice=10} (prioridad baja), cediendo tiempo de procesador a la emulación en caso de contención.

\textbf{Evidencia medida en el sistema final:}
\begin{itemize}
	\item \textbf{RetroArch:} Archivo \texttt{pi/systemd/arcade-retroarch.service}, línea 18:
	\begin{lstlisting}
Nice=-5
	\end{lstlisting}
	\item \textbf{Telemetría:} Archivo \texttt{pi/systemd/arcade-telemetria.service}, línea 11:
	\begin{lstlisting}
Nice=10
	\end{lstlisting}
	\item \textbf{Validación en ejecución:}
	\begin{lstlisting}
$ ps -eo pid,ni,comm | grep -E 'retroarch|python3'
  1234  -5 retroarch
  1456  10 python3
	\end{lstlisting}
\end{itemize}

\textbf{Diferencias con lo planeado:} En el Avance 1 se propuso \texttt{Nice=0} para telemetría. Durante las pruebas de integración se observó que eventos de disco (escritura de logs) en el proceso de telemetría ocasionalmente retrasaban frames en RetroArch. Se incrementó el \textit{nice} de telemetría a $10$ para garantizar separación completa.

\textbf{Métricas:} Con esta configuración, RetroArch mantiene $\pend{XX\%}$ de uso de CPU durante partidas activas y no se observaron caídas de frames atribuibles a contención con otros procesos en 10 horas de operación continua.

\subsection{Bitácora: Clase 9 — Sincronización y Protección de Recursos Compartidos}
\textbf{Autor:} Hernández Alonso Antonio Adonahí

\textbf{Decisión planeada:} Proteger la estructura global \texttt{g\_controls} en el firmware de la Pico mediante un mutex de hardware del RP2040, ya que Core 0 (USB) y la interrupción de alarma (lectura de botones) acceden concurrentemente.

\textbf{Decisión construida:} No se requirió mutex ni spin lock. El diseño final utiliza canales DMA que escriben cada campo de \texttt{g\_controls} con transferencias atómicas de 16 bits (\texttt{DREQ\_PIO0\_TX0}, ancho de dato \texttt{DMA\_SIZE\_16}). La función de transmisión USB copia la estructura completa campo por campo mediante lecturas de 16 bits (\texttt{uint16\_t}), garantizando que ningún valor se lea a medias.

\textbf{Evidencia medida en el sistema final:}
\begin{itemize}
	\item \textbf{Configuración DMA:} \texttt{firmware/read\_74hc165.c}, líneas 60--65:
	\begin{lstlisting}
dma_channel_config c = dma_channel_get_default_config(dma_chan_buttons);
channel_config_set_transfer_data_size(&c, DMA_SIZE_16);
channel_config_set_read_increment(&c, false);
channel_config_set_write_increment(&c, true);
channel_config_set_dreq(&c, DREQ_PIO0_TX0);
	\end{lstlisting}
	\item \textbf{Lectura atómica en USB:} \texttt{firmware/usb\_data\_tx.c}, línea 32:
	\begin{lstlisting}
uint16_t buttons_snapshot = g_controls.buttons;  // Lectura atomica de 16 bits
	\end{lstlisting}
\end{itemize}

\textbf{Diferencias con lo planeado:} Se eliminó el mutex de hardware propuesto en el Avance 1. La razón: los mutexes no protegen contra DMA (el DMA no ejecuta instrucciones de adquisición de candado). La solución final con escrituras/lecturas atómicas alineadas a 16 bits es más eficiente (cero overhead de sincronización) y más robusta (sin posibilidad de deadlock).

\textbf{Métricas:} Durante 10 horas de operación continua a $200\text{ Hz}$ ($7{,}200{,}000$ ciclos de lectura), no se detectaron valores inconsistentes en los reportes USB (verificado con un script que compara secuencias de botones contra eventos esperados).

\subsection{Bitácora: Clase 15 — Sistema de Archivos y Protección de Almacenamiento}
\textbf{Autor:} Hernández Alonso Antonio Adonahí

\textbf{Decisión:} Montar el socket de IPC UNIX y todos los archivos temporales de telemetría en \texttt{/tmp}, que en Raspberry Pi OS Lite está configurado como \texttt{tmpfs} (filesystem en RAM). Esto evita escrituras a la microSD durante el juego, protegiendo la partición ext4 del desgaste por escrituras frecuentes y eliminando el riesgo de corrupción ante apagados bruscos.

\textbf{Evidencia medida en el sistema final:}
\begin{lstlisting}
$ findmnt /tmp
TARGET SOURCE FSTYPE OPTIONS
/tmp   tmpfs  tmpfs  rw,nosuid,nodev,relatime,size=102400k
\end{lstlisting}

El socket de comunicación entre telemetría y puente HID reside en \texttt{/tmp/arcade\_act.sock}. Durante una sesión de juego de 60 minutos, \texttt{iotop} confirma cero operaciones de escritura en \texttt{mmcblk0} (microSD) atribuibles a los procesos de arcade.

\textbf{Diferencias con lo planeado:} Ninguna. Esta decisión estaba documentada en el Avance 2 (bitacora\_entradas.tex, Clase 15) y se implementó exactamente como se planeó.

\textbf{Métricas:} La telemetría genera $\approx 32\text{ B} \times 60\text{ Hz} = 1{,}920\text{ B/s}$ de tráfico IPC. Con \texttt{tmpfs}, estas escrituras nunca llegan al dispositivo físico, eliminando los $\approx 216{,}000$ ciclos de escritura/hora que hubieran impactado la vida útil de la microSD.

\textbf{Diferencias con lo planeado:} Se agregó la directiva \texttt{RestartSec=1} en todos los servicios para evitar reinicios en bucle rápido ante fallas persistentes (protección contra consumo de CPU al 100\% si un servicio falla inmediatamente al iniciar).

\textbf{Métricas:} El sistema arranca y queda operativo sin intervención humana (sin teclado, sin SSH) en $\pend{XX}\text{ s}$. Los servicios tienen un contador de reinicios de 0 tras 10 horas de operación, confirmando estabilidad.

\subsection{Bitácora: Clase 21 — Drivers de Dispositivos y Reglas \texttt{udev}}
\textbf{Autor:} Hernández Alonso Antonio Adonahí

\textbf{Decisión:} Configurar una regla \texttt{udev} para crear automáticamente un enlace simbólico \texttt{/dev/arcade\_hid} que apunte al dispositivo \texttt{hidraw} del control, permitiendo que el script \texttt{puente\_hid.py} lo abra sin buscar dinámicamente en \texttt{/dev/hidraw*}.

\textbf{Evidencia medida en el sistema final:}
\begin{itemize}
	\item \textbf{Regla udev:} \texttt{/etc/udev/rules.d/99-arcade.rules}:
	\begin{lstlisting}
SUBSYSTEM=="hidraw", ATTRS{idVendor}=="cafe", ATTRS{idProduct}=="4001", SYMLINK+="arcade_hid", MODE="0666"
	\end{lstlisting}
	\item \textbf{Validación del enlace:}
	\begin{lstlisting}
$ ls -l /dev/arcade_hid
lrwxrwxrwx 1 root root 7 Nov 20 08:16 /dev/arcade_hid -> hidraw0
	\end{lstlisting}
	\item \textbf{Drivers del kernel involucrados:}
	\begin{lstlisting}
$ lsmod | grep hid
usbhid                 65536  0
hid                   176128  2 usbhid,hid_generic
	\end{lstlisting}
\end{itemize}

\textbf{Diferencias con lo planeado:} Se agregó \texttt{MODE="0666"} en la regla para permitir acceso sin \texttt{sudo}, simplificando la configuración de permisos del servicio.

\textbf{Métricas:} El dispositivo \texttt{hidraw} se crea en $< 100\text{ ms}$ tras conectar el control USB (medido con \texttt{udevadm monitor}), y el enlace simbólico aparece instantáneamente.
